# AgL Modules

AgL has a file-based module system. Every production program is loaded into a `ModuleGraph`: the entry module and its transitive imports. Unless the host disables it or a module explicitly imports `std/core`, every loaded entry and library module except `std/core` itself receives an automatic `import std/core::*` prelude. Program-level scope, typecheck, match compilation, and lowering passes orchestrate per-module workers over that loaded program. The AST, value model, and evaluator are shared throughout (see [index.md](index.md)).

## Module Identity and Roots

A module is identified by a slash-separated path (`foo/bar`) mapping to a relative `.agl` file; a sentinel id keys the entry program. `ModuleId` construction and display use this path form, while its segments remain the shared internal identity. Modules are found by searching an unordered, canonicalized set of *roots* — the invocation directory, the selected standard library, a global library root, configured roots, CLI roots, and mounted package roots. Ordinary roots are loose, while a package-only root exposes only files inside that package's declared module-tree directory. A package-owned entry does not expose its containing directory as a loose root; if a package path is explicitly supplied as an ordinary root, its loose semantics remain. Standard-library selection is exclusive of package-root mounting: an `AGM_STDLIB` override or shipped fallback (wheel-bundled or source-checkout) never adds an active `std` package as another root. Package inputs carry both their root and manifest ownership metadata, so development directories and future package sources use the same assembly seam. Resolution requires exactly one match across all eligible roots: zero is "not found", two distinct files is "ambiguous". There is deliberately no first-root-wins shadowing. Wildcard imports use the same mount scoping and global-uniqueness rules.

## Loading

The loader's shared entry parser canonicalizes the entry path, derives its diagnostic source id, and collects lexical advisories; `load_graph` and the pipeline's split entry parse both use it. Loading then does a breadth-first traversal of transitive imports, parsing each module so that node ids are globally unique across all modules — a prerequisite for the shared side-table convention. Traversal terminates when a module is already loaded, which makes import cycles finite and safe; cycles are allowed, but an import that resolves back to the entry file is rejected. Before an edge is loaded, canonical paths identify whether its source and target belong to mounted packages or the host-selected standard-library root. A package module may reach its own modules only under its package-qualified IDs, that standard library, and mounted packages named by its manifest dependencies; a loose module sharing a dependency name is not package-owned. Ad-hoc source remains unrestricted. The result is a module graph carrying each module's AST, canonical path, source id, imports, and import/export adjacency, plus strongly-connected-component information for diagnostics. Consumers that need transitive module reachability use that adjacency rather than scope contributions. Traversal is deterministic regardless of filesystem or root ordering. Import, use, and export extraction descends into named scope regions. Region-nested imports and exports are graph edges exactly like root declarations; uses are retained for scope resolution without adding a disk edge.

A module declaring an `extern def` at any scope path (Python FFI) needs a companion Python file at its own path with a `.py` suffix. A scoped extern resolves its final member name in that companion; two scoped declarations cannot map to the same member name. The companion path is derived from the module's canonical path, not searched, so root-ambiguity rules never apply to it; the loader records it and verifies it exists during graph loading, while the import itself happens in the execution layer ([execution/evaluator.md](execution/evaluator.md)). The stdlib's companion-backed surface includes `std/text` for name-only interpolation and `std/fs` for text filesystem effects; `std/fs` delegates to the shared dry-run-aware filesystem primitive layer, so it uses the same invocation working-directory behavior as other host filesystem operations.

## Program Passes

Program passes coordinate the module workers while preserving cross-module forward references and mutual recursion:

- **Scope.** A whole-program pre-pass computes per-module export maps — each declared path atom mapped to its originating module and declaration path, with re-export chains resolved to their origin — and collects every declaration before any body is resolved. Per-module collection keys declarations by scope path as well as name, merges repeated scope regions and shorthand declarations, and records declarations, parameters, and bindings consistently across modules and regions. An import contributes its complete public qualified surface, apart from hidden paths; a positive tail adds selected public paths to the bare namespace without narrowing the qualified surface. Region-scoped tails are snapshotted onto their region's scope node while their qualifier routes remain module-wide. `use` declarations resolve an already-nameable local or imported scope and contribute its selected members to the enclosing scope layer; they have no graph edge. Region-scoped exports re-root forwarded atoms under the region path. Export brace tails select forwarded paths, while plain exports and hiding operate on the full public surface. Ordinary re-export cycles that preserve names remain valid; propagation rejects a cycle that continues expanding a scoped path. Import aliases replace plain-path routes, and wildcard declarations distribute tails and clauses per matched module. Suffix (`suffix::name`), anchored (`/path::name`), self (`::name`), constructor, and type references all use the same contribution resolver; ambiguities fail at the use site. A nominal alias is a cross-module constructor candidate only when its chain provably ends at a constructible type, judged from its declaring module's own environment. Every module root is static: declarations, parameters, and constant bindings are allowed, while bare expressions and assignments are rejected. The constancy half of that rule exists so importing a module executes nothing, so it does not apply to a root carrying a host-synthesized entry (`syntax/nodes.py::declares_synthetic_entry`): such a source is an inline command whose root bindings are the ones the entry transform kept there. Each module's resolution carries its origin path and whether the module declares a `program def` of its own, so scope and typecheck phrase a static-root rejection in shared wording from `agl/diagnostics.py`, adding the inline-module explanation only for file-less source that declares its own entry. Params are likewise legal in every module's named scope regions. Parameter discovery walks the module graph adjacency: a program receives the params declared in its own module and its transitive import/export dependencies. Lowering retains each param's declaring module so every reachable module can read its host-installed binding. The incremental REPL is the sole host that admits executable root items. Every module root and every region's own item sequence enforces header-only ordering of imports, uses, and exports, tracked independently per block, so a region is one item for its enclosing block's ordering while its own items get their own header rule.
- **Typecheck.** Function signatures retain declaration paths alongside node identity, so scope members receive the same header collection and candidate inference as root functions. A type's identity is the declaration that introduced it; module, scope path, and name are resolution/display metadata, so same-spelled root and scoped types remain distinct declarations. Because nominal types are shape-free handles ([frontend/types.md](frontend/types.md)), declarations resolve in a fixed order with no dependency ordering — forward references and type cycles spanning modules work exactly like same-module ones, while alias cycles remain illegal. The resolved-program artifact preserves the loader's reverse-topological import SCCs. After collecting explicit, builtin, and extern headers, typecheck traverses those SCCs dependencies first: closed unannotated candidates publish by declaration node id before importers, while an import cycle shares one cross-module function graph. It then authoritatively checks each module body with the completed concrete signature table. The whole-table analyses run once over the shared `TypeTable`.
- **Match compilation.** Every source `case` and destructuring immutable `let` in every checked module is compiled, including sites entry code never calls. Simple-name and `_` lets are irrefutable and lower directly, so they are omitted from the decision mapping. The program artifact carries a total per-module mapping for the collected sites; case coverage/redundancy and refutable-let issues prevent lowering and are reported with their originating source labels. Lowering consumes the same decisions in action mode for cases and binding mode for destructuring lets.
- **Lowering.** The checked artifact retains the loader's reverse-topological import SCCs for this execution-sensitive pass, separate from the checker's presentation order. The program links into one executable program; execution narrows initialization, parameter validation, and dry-run call-site metadata to the selected program module's dependency graph, whose library initializers run in dependency/SCC order with that module last. Cross-module calls use linked ids directly, never resolver or checker side tables. The selected module remains attached to cached executables across capability-driven relowering, and extern wiring is restricted to that same runtime graph.

## Source Attribution

Every source span carries a source id identifying its origin file, so multi-file diagnostics name the right file. Span positions compare equal across files (the source id is excluded from equality), consistent with how node ids are excluded from AST equality. Diagnostics carry the source label through to formatting, including related notes that can point into other modules.
